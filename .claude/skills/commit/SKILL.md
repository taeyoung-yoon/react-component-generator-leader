# commit

변경사항을 읽고, 의미 있는 단위로 나누어, 컨벤션에 맞는 한국어 메시지로 커밋한다. 사용자가 커밋을 요청한 시점에 이미 의도가 확인된 것이므로, 별도 승인 절차 없이 바로 커밋한다. 대신 어떤 기준으로 나누고 무엇을 제외했는지는 커밋 후 투명하게 보고한다.

## 절차

### 1. 변경사항 분석
다음을 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 이 저장소의 기존 메시지 톤 확인
```

- git 저장소가 아니거나 변경사항이 없으면 그 사실만 알리고 멈춘다.
- 이미 staged 된 파일이 있다면 사용자가 의도해서 올린 것이므로 존중한다. 임의로 unstage 하지 않는다.
- untracked 파일은 내용을 읽어 커밋 대상인지 판단한다.

### 2. 논리적 단위로 분류
한 커밋은 한 가지 목적만 담는다. 나중에 `git revert`나 `git bisect`로 되돌리거나 추적하기 쉽게 하기 위해서다.

- 서로 다른 목적(기능 추가 + 무관한 버그 수정 + 설정 변경)이 섞여 있으면 파일, 필요하면 hunk 단위로 나눈다.
- 하나의 기능에 딸린 코드·테스트·타입 변경은 같은 커밋에 둔다.
- 단일 목적이면 커밋 하나로 충분하다. 억지로 쪼개지 않는다.
- 아래는 커밋 대상에서 제외하고 사용자에게 알린다.
  - `.env`, 키·토큰·비밀번호가 들어간 파일 (값은 출력하지 않고 파일명만 언급한다)
  - `node_modules`, 빌드 산출물, 로그 등 `.gitignore`에 있어야 할 파일
  - 디버깅용 `console.log`, 임시 파일처럼 남기면 안 될 것으로 보이는 변경

### 3. 한국어 커밋 메시지 작성
형식: `타입: 요약`

| 타입 | 용도 |
|---|---|
| feat | 사용자에게 보이는 새 기능 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 설정, 의존성, 빌드, 문서 등 잡무 |

- 요약은 한국어로, 50자 안팎의 한 줄. "무엇을 했는지"보다 "무엇이 달라졌는지"가 드러나게 쓴다. 마침표는 붙이지 않는다.
- 요약만으로 이유가 전달되지 않으면 빈 줄 뒤에 본문을 붙여 **왜** 바꿨는지 적는다. 코드를 보면 알 수 있는 "어떻게"는 적지 않는다.
- 저장소의 기존 로그에 이미 다른 컨벤션(scope 사용 등)이 있으면 위 형식을 해치지 않는 선에서 맞춘다.
- 하네스가 커밋 attribution(Co-Authored-By)을 지시하면 메시지 끝에 붙인다.

예시:
```
feat: 컴포넌트 생성 요청에 스트리밍 응답 지원 추가
fix: 빈 프롬프트 제출 시 서버 오류가 나던 문제 수정
refactor: 프롬프트 빌더를 별도 모듈로 분리
chore: eslint 설정에서 미사용 규칙 제거
```

### 4. 커밋 실행
분류한 단위마다 해당 파일만 `git add <파일>`로 올리고 `git commit`한다. `git add -A`·`git add .`는 제외하기로 한 파일까지 휩쓸기 때문에 쓰지 않는다. hunk 단위 분리가 필요하면 `git add -p` 대신 비대화형으로 가능한 방법(패치 파일 적용 등)을 쓴다.

- 훅 실패 시 `--no-verify`로 우회하지 않는다. 원인을 알리고 수정 방향을 제안한다.
- `git push`는 요청받지 않았으면 하지 않는다.
- 끝나면 `git log --oneline -n <커밋 수>`로 결과를 보여주고, 제외한 파일이 있으면 이유와 함께 알린다(비밀값은 파일명만).
- 의도가 모호해 단위를 정하기 어렵거나(예: 같은 파일에 무관한 변경이 얽힌 경우) 커밋하면 안 될 것 같은 파일이 있으면, 그 부분만 사용자에게 묻고 나머지는 진행한다.
