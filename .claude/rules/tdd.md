# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.**
> 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"로 처리하지 않는다.

## 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙을 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 침묵하는 부분에만 적용한다.

## 적용 기준

### 반드시 적용

- **비즈니스 로직**
- **API** (라우트 핸들러, 외부 호출 래퍼, 응답 처리)
- **유틸 / 순수 함수**
- **버그 수정** (버그를 재현하는 실패 테스트가 먼저)

### 불필요

- **타입 정의** (`interface`, `type`)
- **설정 파일** (빌드, 린트, tsconfig 등)
- **순수 UI** (로직 없는 마크업·스타일)
- **SQL** (스키마, 마이그레이션, 단순 쿼리)

애매하면 **적용 대상으로 취급**한다.

## RED-GREEN-REFACTOR

### 1. RED — 실패하는 테스트

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- **반드시 실행해서 실패를 확인한다.** 실행하지 않은 테스트는 테스트가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 잘못된 셋업으로 인한 실패는 RED가 아니다. 테스트를 고쳐 올바른 이유로 실패시킨다.

### 2. GREEN — 통과시키기

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI**: 아직 테스트가 요구하지 않는 기능, 분기, 옵션을 넣지 않는다.
- **신규 테스트와 기존 테스트를 모두 실행해** 전부 통과하는지 확인한다.

### 3. REFACTOR — 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green 상태를 유지**한다. 수정 후마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED부터 시작한다.

### 4. 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 임시 파일, 복사해 두기 모두 포함한다. 보고 베끼면 그것은 테스트 선행이 아니다.

## 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드가 가장 많이 깨진다. 테스트도 30초면 쓴다. **단순하면 더 쉽게 테스트할 수 있다.** |
| "나중에 추가하겠다" | 나중에 쓴 테스트는 이미 통과한다. **실패를 본 적 없는 테스트는 아무것도 증명하지 않는다.** |
| "시간이 없다" | 디버깅과 회귀 수정이 더 오래 걸린다. **TDD는 느린 길이 아니라 재작업을 줄이는 길이다.** |
| "삭제하면 낭비다" | 매몰비용이다. 검증 안 된 코드를 유지하는 비용이 더 크다. **다시 쓰는 건 빠르다.** |
| "프로토타입이다" | 프로토타입은 프로덕션이 된다. 적용 대상이면 **프로토타입도 예외 없다.** |
